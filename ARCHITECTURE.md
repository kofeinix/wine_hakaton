# Архитектура

Как устроен сервис: пайплайн поиска по фото и границы слоёв. Запуск, переменные окружения и
ограничения описаны в [README.md](README.md).

Разделы 2–6 идут по шагам пайплайна из ТЗ: **нормализация фото → извлечение признаков → поиск по
каталогу → выдача карточки → дополнительный функционал**. Ссылки ведут на файлы и функции, а не на
номера строк: числа и пороги в тексте совпадают с константами в коде на момент написания.

---

## 1. Общая схема

```
 браузер (Nuxt SPA, mobile-first)                         проверочный скрипт организаторов
            │  /api/v1/*  (прокси Nitro)                            │ POST :8080/v1/eval/predict
            ▼                                                       ▼
 ┌──────────────────────────────── app (FastAPI, один процесс) ─────────────────────────────┐
 │ HTTP-слой      routes.py, user_routes.py, auth.py                                        │
 │ Сервисы        WineService (поиск) · SommelierService · TermService · UserService ·      │
 │                AchievementService · ReminderWorker (фоновая задача)                      │
 │ Репозиторий    WineRepository (SQL к каталогу)                                           │
 │ ML             YOLO-кропы · SigLIP2-384 · адаптер векторов · OCR-матчинг текста           │
 │ Подключения    PostgreSQL · Qdrant · MinIO · Redis · vision-LLM (OpenAI-совместимый API)  │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
      │ каталог, пользователи    │ векторы фото     │ фото          │ семафор LLM   │ OCR этикетки
      ▼                          ▼                  ▼               ▼               ▼
  PostgreSQL                   Qdrant             MinIO           Redis      LM Studio / Ollama /
                                                                             vLLM / облачный API
```

Всё поднимается одной командой `docker compose up`. Разовые сервисы `models-init`, `data-init`,
`db-init`, `qdrant-init`, `minio-init` скачивают модели и данные и заполняют хранилища; `app` стартует
после них. Повторный запуск эти шаги пропускает.

### Слои backend

Зависимости идут только сверху вниз: `src/ml` и `src/llm` ничего не знают про `src/api`.

| Слой | Модули | Отвечает за | Не делает |
|---|---|---|---|
| HTTP | `src/api/routes.py`, `src/api/user_routes.py` | разбор запроса, валидация, вызов сервиса, сборка ответа, запись в историю | не обращается к БД и клиентам напрямую |
| Auth | `src/api/auth.py` | JWT (HS256), bcrypt, анонимная cookie для истории без входа | — |
| Сервисы | `src/api/services/*` | сценарии: пайплайн поиска, сомелье, пользователи, достижения, кеши | не пишут SQL каталога |
| Репозиторий | `src/api/repositories/wine_repository.py` | SQL к каталогу: карточки, фото, срез полей для OCR | не знает про HTTP |
| ML | `src/ml/*` | модели и чистые алгоритмы: YOLO, SigLIP2, адаптер, формула OCR-матчинга, нормализация текста | не импортирует `src.api` |
| LLM | `src/llm/langchain_openai.py` | клиент vision-LLM: ретраи, ограничение параллелизма, промпт OCR | — |
| Подключения | `src/connections/*` | тонкие клиенты PostgreSQL, Qdrant, MinIO, Redis, rate-limiter | без доменной логики |
| Настройки | `src/settings/*` | pydantic-settings из `.env` (`РАЗДЕЛ__ПАРАМЕТР`), логирование | — |
| Сборка | `src/container/*` | `ConnectionManager` создаёт и запускает все клиенты и модели, `AppContainer` отвечает за жизненный цикл и сигналы | — |

Сервисы создаются один раз в `create_app` (`src/api/app.py`) и лежат в `app.state`; роутеры
получают их через `Depends`, без глобальных переменных.

### Frontend

`frontend/` — Nuxt 3 в режиме SPA (`ssr: false`). Nitro проксирует `/api/**` на backend, поэтому
браузер работает с одним адресом. Вкладки: «Сканер» (`ScannerPage`, `WineResult`, `SearchDiagnostics`),
«Сомелье» (`SommelierPage`, `SommelierFilters`, `SommelierRegions`), профиль (`ProfilePage`). Состояние
и вызовы API собраны в `composables/useWineApp.js`. Сайт можно установить на экран «Домой»
(`manifest.webmanifest`).

## 2. Нормализация фото

`WinePhotoService.build_query_views` (`src/api/services/photo_service.py`) превращает загруженный
файл в три **ракурса** (view). Дальше поиск идёт по каждому ракурсу отдельно.

| view | что это | как получено |
|---|---|---|
| `original` | всё фото | `open_rgb_image` (`src/ml/utils.py`): поворот по EXIF и приведение к RGB |
| `bottle_crop` | бутылка | YOLO `yolo26x.pt` (COCO), класс 39 «bottle», поля 4% |
| `label_crop` | этикетка | YOLO `models/yolo/label.pt` — своя модель детекции этикеток |

Порядок и деградация:

1. Бутылка ищется на всём фото.
2. Этикетка ищется на всём фото с бонусом за попадание внутрь найденной бутылки
   (`preferred_region_weight = 0.25`). Если не нашлась — повторный поиск внутри кропа бутылки.
3. Если этикетки нет ни там, ни там, в роли `label_crop` выступает всё фото
   (`source_view = "original_fallback"`): с него читает текст OCR, но в векторном поиске этот ракурс
   не участвует (см. ниже).
4. Ошибка YOLO не роняет запрос: кроп считается ненайденным.

Устройство для YOLO выбирается так же, как для SigLIP2 (`resolve_device`, `src/ml/utils.py`):
CUDA → MPS → CPU, либо явно через `YOLO__DEVICE`.

Из нескольких детекций выбирается одна по взвешенной сумме уверенности, близости к центру кадра и
площади (`UltralyticsCropper._select_best_box`, `src/ml/yolo.py`). Все детекции с уверенностью от
0.25 возвращаются в ответе: по ним фронтенд рисует рамки, и на фото полки пользователь выбирает
нужную бутылку.

Детали, которые влияют на точность:

- Ultralytics считает numpy-массив изображением BGR, поэтому RGB из PIL переворачивается перед
  детекцией. Без этого красное вино «синеет» и детекции теряют уверенность.
- Перед поиском файл проверяется декодированием (`src/api/utils.py`): битый файл или не-изображение
  дают 415, а не 500 в глубине пайплайна. `Content-Type` не проверяется, потому что часть клиентов
  шлёт webp или heic как `application/octet-stream`.

### Какие ракурсы идут в поиск — `select_views` (`src/api/services/visual_search.py`)

- **Крупный план этикетки.** Если этикетка занимает больше 60% кадра и уверенность больше 0.5,
  ищем только по `label_crop`: остальные ракурсы здесь только добавляют шум.
- **Этикетка не найдена.** Ищем по всему фото и кропу бутылки, без ракурса «этикетка»: всё фото
  среди кропов этикеток каталога ищется хуже, чем среди полных фото. Так бывает на полке и при съёмке
  вплотную; на реальных фото это подняло top-1 с 92,5% до 98,5% (4 исправленных фото, ни одного
  испорченного). Режим крупного плана при этом не включается.
- **Полка.** Если на фото найдено 3 этикетки и больше, ракурс `original` выключается: он описывает
  полку, а не нужное вино.
- Параметр `views` в `/search/image/extended` задаёт ракурсы явно, для экспериментов; автоматические
  режимы его не переопределяют.

## 3. Извлечение признаков

### 3.1 Визуальные признаки — SigLIP2 + адаптер

- Модель `google/siglip2-base-patch16-384` (`src/ml/siglip2.py`), локально из `models/siglip2_384`.
  Устройство выбирается автоматически: CUDA → MPS (Apple) → CPU, либо задаётся `EMBEDDINGS__DEVICE`.
- Один L2-нормированный вектор на ракурс; все активные ракурсы кодируются одним батчем.
- Поверх вектора работает **дообученный адаптер** (`src/ml/view_adapter.py`), свой для каждого
  ракурса: `f(x) = normalize(x + B·A·x)`, ранг 64. Он обучен сводить фото «из жизни» (полка, руки,
  свет) с фото того же вина в каталоге и разводить соседние вина одной линейки
  (`scripts/train_view_adapter.py`, данные и замеры — в README). Адаптер применяется одинаково к
  запросу и к фото каталога при загрузке в Qdrant; файл весит 1 МБ и лежит в репозитории.
- Версия адаптера (md5 файла) входит в имя коллекций Qdrant: после переобучения векторы каталога и
  запроса не могут разойтись.

По сути адаптер — это нормализация на уровне признаков: он убирает из вектора то, чем фото с полки
отличается от студийного фото каталога (фон, свет, ракурс).

### 3.2 Текст этикетки — vision-LLM (необязательный этап)

`ChatOpenAIWrapper.ocr_image_text` (`src/llm/langchain_openai.py`):

- Источник: `label_crop` → `bottle_crop` → `original` (`ocr_source_view`).
- Картинка уменьшается до 1024 px по большей стороне и уходит в модель как `data:image/jpeg`.
- Промпт просит вернуть только видимый текст, обратить внимание на производителя, название, сорт,
  цвет и сахар, а диакритику транслитерировать.
- Результат кешируется (LRU на 512 записей по sha1 JPEG-кропа): повторный поиск того же фото не
  обращается к LLM.
- Параллельные запросы к LLM ограничены семафором в Redis (`RATE_LIMITER__LIMITERS`, по умолчанию 1).
- Подходит любой OpenAI-совместимый сервер: LM Studio, Ollama, vLLM (`./run_llm.sh`) или облачный
  API. Для моделей с рассуждениями есть `LLM__DISABLE_REASONING`.
- LLM необязательна. При старте `ConnectionManager._start_llm` (`src/container/manager.py`) проверяет,
  что сервер отвечает и модель есть в его списке (не дольше 15 с). Если `LLM__BASE_URL` /
  `LLM__MODEL_NAME` не заданы или сервер недоступен, в лог пишется предупреждение, клиент LLM не
  создаётся, а поиск идёт только по изображению (`ocr.reason = llm_unavailable`). Чтобы включить OCR
  после запуска LLM, нужно перезапустить `app`.

## 4. Поиск по каталогу

Оркестратор — `WineService.search` (`src/api/services/wine_service.py`):

```
кропы (YOLO) ─► отбор ракурсов ─┬─► эмбеддинги SigLIP2 + адаптер ─► Qdrant по каждому ракурсу ─► агрегация ─┐
                                └─► OCR этикетки (vision-LLM) ─────────────────────────────────────────────┤
                                                                                                           ▼
                                       пропуск OCR, если визуальный результат уверенный ─► OCR-реранк ─► top-N
```

OCR и визуальный поиск стартуют одновременно: первый ждёт LLM, второй — модель и Qdrant.

### 4.1 Векторный поиск — `VisualSearcher.search`

- Коллекции Qdrant `wine_{view}_siglip2_384_{версия адаптера}`, по одной на ракурс, метрика cosine.
  В них около 23 тыс. фото: главное фото каждого вина с портала, фото с Яндекса и сгенерированные
  сцены (бутылка на полке, на столе и в руках при разном свете).
- Запросы к активным ракурсам идут параллельно, по 150 ближайших фото на ракурс, с payload
  (`wine_id`, `slug`, `photo_id`). Точки без `wine_id` отбрасываются.

### 4.2 Агрегация фото в вина — `group_by_wine`

```
скор ракурса = 0.75 × лучшее фото + 0.25 × среднее трёх лучших фото вина
вклад ракурса = вес ракурса × скор ракурса
скор вина     = 0.7 × max(вкладов) + 0.3 × sum(вкладов)
```

Веса ракурсов: `label_crop 0.55`, `original 0.30`, `bottle_crop 0.15`. Они нормируются по ракурсам,
которые реально вернули результаты. Максимум вместо суммы нужен, чтобы слабый дополнительный ракурс
не ухудшал результат: главный сигнал решает, остальные дают ограниченный бонус. В пул уходят
50 лучших вин, даже если клиент просит меньше.

### 4.3 OCR-реранк — `OcrMatchService` → `src/ml/ocr_matching.py`

```
final_score = visual_score + ocr_bonus
```

`ocr_bonus` складывается из:

- сходства названия, производителя и сортов с текстом этикетки (IDF-покрытие слов, бонус начисляется
  выше порога);
- **уникальных доказательств**: суммы редкостей (IDF по пулу кандидатов) слов названия и
  производителя, найденных на этикетке. Слово, общее для всей линейки, весит 0; слово, которое есть
  только у одного кандидата, — много. Это главный сигнал для near-duplicates одного производителя;
- штрафов за явные противоречия: на этикетке другой цвет, сахар, сорт или производитель;
- бонуса за совпадение крепости.

Отсутствие чего-либо в тексте **не штрафуется**: LLM часто читает этикетку частично. Строки
сравниваются в трёх вариантах — как есть, RU→LAT и LAT→RU, — потому что сорта и производители в
каталоге записаны то латиницей, то кириллицей. Словарь каталога (IDF, синонимы цветов и сахаров)
строится один раз и кешируется. Веса формулы подобраны кросс-валидацией на отложенных фото; менять
их имеет смысл только с прогоном `scripts/eval_search.py`.

### 4.4 Когда OCR пропускается

OCR добавляет секунды, поэтому его результат ждут не всегда:

- **Уверенный визуальный результат.** Если визуальный top-1 опережает top-2 больше чем на 15%
  (`(v1 − v2) / v2 > SEARCH__OCR_SKIP_VISUAL_GAP = 0.15`) **и** сам скор top-1 не ниже
  `SEARCH__OCR_SKIP_MIN_SCORE = 0.50`, задача OCR отменяется (`reason = skipped_confident_visual`).
  На отложенных фото Vivino текст этикетки менял top-1 только при отрыве до 0.077; при пороге 0.15
  OCR пропускается примерно в 2/3 поисков без потери точности. Слабый top-1 с большим отрывом
  (вина нет в каталоге, сложное фото) всё равно проверяется текстом.
- **Бюджет времени.** Если LLM не ответила за `SEARCH__OCR_BUDGET_SECONDS = 7.5` с от начала
  поиска, ответ строится по изображению (`reason = timeout_budget`). Проверочный скрипт организаторов
  ждёт ответ не дольше 10 с.
- **Ошибка LLM** (`ocr_failed`) или пустой текст (`empty_ocr_text`) — поиск продолжается по
  изображению.

### 4.5 Параллельность

YOLO и SigLIP2 выполняются в отдельном потоке (`ThreadPoolExecutor(max_workers=1)`), чтобы не
блокировать event loop. Поток один: Ultralytics не потокобезопасен. При старте приложения идёт
прогревочный поиск по пустой картинке: модели загружаются заранее, и первый настоящий запрос не ждёт
их загрузки.

## 5. Выдача карточки

| Эндпоинт | Ответ | Для кого |
|---|---|---|
| `POST /v1/eval/predict` (порт `EVAL_PORT`, 8080) | `{"slug": "..."}` | проверочный скрипт организаторов; в историю не пишется |
| `POST /api/v1/search/image` | `{"slug": "..."}` | простая интеграция |
| `POST /api/v1/search/image/extended` | результаты с карточками и диагностикой | интерфейс сканера |
| `GET /api/v1/wines/{id}` | карточка вина | страница вина |
| `GET /api/v1/photos/{id}` | фото из MinIO (webp для главного фото, иначе jpg) | карточка, галерея |

Ответ `/search/image/extended` (`SearchResponse`, `src/api/schemas.py`):

- `status` — `found` / `not_found`;
- `results[]` — кандидаты по убыванию `final_score` с разложением `visual_score` + `ocr_score` и
  `similarity`: итоговый скор, делённый на максимально возможный в этом поиске
  (`src/api/services/similarity.py`), то есть 0–100%, сравнимое между разными фото;
- `results[].wine` — полная карточка: производитель, регион, год, цвет, сахар, крепость, сорта,
  температура подачи, гастросочетания, описание, рейтинг, фото. Карточки всех кандидатов грузятся
  одним запросом (`WineRepository.load_wines_by_ids`) и собираются одной функцией
  `wine_to_response` — той же, что для истории, избранного и уведомлений;
- `ocr` — распознанный текст, с какого кропа читали, взят ли из кеша, почему пропущен;
- `crops`, `detections`, `image` — рамки кропов и все найденные бутылки и этикетки;
- `search` — активные ракурсы и режимы (крупный план этикетки, полка);
- `timings_ms` — время этапов: `crops_ms`, `embedding_ms`, `vector_search_ms`, `ocr_ms`,
  `rerank_ms`, `total_ms`;
- `diagnostics` — полная отладка (пул кандидатов, признаки OCR-формулы), только при `debug=true`.

Интерфейс показывает первый результат как найденное вино, следующие — как «Похожие варианты».
Вкладка диагностики (`SearchDiagnostics.vue`) показывает кропы, время этапов и разложение скора.

### 6.1 Сомелье — `src/api/services/sommelier_service.py`

Каталог (~2 тыс. вин) при первом запросе целиком загружается в память; фильтры, счётчики вариантов
и ранжирование считаются на Python. Подбор идёт по поводу (аперитив, ужин, подарок, компания,
свидание, пикник, мангал, десерт), группам блюд, вкусу (ключевые слова описания и крепость), типу,
цвету, сахару, региону, сорту и рейтингу. Каждое вино в выдаче сопровождается **причинами**
(`reasons`), взятыми из полей его карточки, поэтому их можно проверить на странице вина. Поиск по
названию понимает латиницу и кириллицу и исправляет опечатки (`difflib`). Изменения каталога
требуют перезапуска `app`.

### 6.2 Словарь терминов — `src/api/services/term_service.py`

Термины (источник — словарь Luding, `scripts/import_wine_terms.py`) лежат в PostgreSQL. API отдаёт
основы слов и допустимые окончания; фронтенд подсвечивает термины в названии и описании вина, по
нажатию открывается определение в чате-справочнике (`WineChat.vue`).

### 6.3 Достижения — `src/api/services/achievement_catalog.py`, `achievement_service.py`

Достижения описаны в коде (`build_catalog`). Прогресс не накапливается событиями, а каждый раз
считается из снимка данных пользователя (сканы, отзывы, реакции, избранное), поэтому всегда
совпадает с фактами. Фронтенд вызывает `POST /achievements/check` после действия пользователя. Скан
засчитывается, только если фото снято кнопкой «Камера» и уверенность поиска не ниже
`SCAN_MIN_CONFIDENCE`.

### 6.4 Напоминания — `src/api/services/notification_worker.py`

Фоновая задача, включается `NOTIFICATIONS__ENABLED`. Раз в `NOTIFICATIONS__CHECK_INTERVAL_SECONDS`
собирает одно сводное напоминание на сессию поисков: вина, просмотренные не раньше
`NOTIFICATIONS__MAX_AGE_HOURS` и спустя `NOTIFICATIONS__DELAY_MINUTES` после последнего поиска. Из
напоминания вино добавляется в избранное или оценивается в один тап.

## 7. Данные и офлайн-подготовка

### Хранилища

| Система | Что лежит | Кто обращается |
|---|---|---|
| PostgreSQL | каталог (вина, производители, регионы, сорта, блюда, фото, термины) и пользовательские таблицы (пользователи, история, избранное, отзывы, уведомления, достижения) | `WineRepository`, сервисы |
| Qdrant | векторы SigLIP2 + адаптер, коллекция на ракурс | `VisualSearcher` (чтение), `scripts/init_qdrant.py` (запись) |
| MinIO | фото каталога, фото отзывов | `MinioClient` |
| Redis | семафоры rate-limiter (параллелизм LLM) | `RateLimiterManager` |

Каталог и пользовательские таблицы живут в одной базе, но обслуживаются по-разному. Каталог
приводится к `data/db/*.json` при каждом запуске (`db-init`, `scripts/init_database.py --prune`);
пользовательские таблицы создаются при старте `app`, если их нет, и `db-init` их не трогает.
Миграций нет: изменение схемы требует `docker compose down -v` или ручного SQL.

### Подготовка каталога (скрипты, в рантайме `app` не участвуют)

```
data/db/*.json ─────────────── init_database.py --prune ──────────► PostgreSQL
фото каталога ─ prepare_image_views.py ─► кропы бутылки и этикетки
              ─ generate_qwen_image_edit_views.py / generate_flux2_klein_views.py ─► сгенерированные сцены
              ─ index_siglip2_views_qdrant.py ─► data/embeddings/siglip2_384/{original,bottle_crop,label_crop}.npz
                                                    │
                          train_view_adapter.py ◄───┤  (обучение адаптера → models/adapter/siglip2_384_views.npz)
                                                    ▼
                                 init_qdrant.py: векторы через адаптер ─► Qdrant; старые коллекции удаляются
              ─ build_photos_archive.py ─► data/photos.tar.gz ─► minio-init ─► MinIO
```

Готовые эмбеддинги и архивы фото `data-init` скачивает с Яндекс Диска (`scripts/download_data.py`),
модели — `models-init` (`scripts/prepare_models.py`): YOLO-детектор бутылок и SigLIP2 с Hugging Face.
Своя модель этикеток и адаптер лежат в репозитории. `qdrant-init` и `minio-init` пропускают загрузку,
если данные уже на месте (перезалить: `init_qdrant.py --recreate`, `MINIO_RESEED=1`).

Генерация сцен требует `diffusers` и `torchao`, которых нет в `pyproject.toml`: эти скрипты
запускаются в отдельном окружении с GPU. Для воспроизведения сервиса они не нужны — их результат
входит в скачиваемые эмбеддинги.

### Оценка качества

`scripts/eval_search.py` прогоняет отложенные фото через `/search/image/extended` и считает
Accuracy@1, MRR, Recall@k, средние скоры верных и ошибочных ответов и время ответа. Проверка формата
организаторов — `eval/participant_test.sh` на порту 8080.

## 8. Отличия от рекомендованного стека

| Рекомендовано в ТЗ | У нас | Почему |
|---|---|---|
| Backend на Nuxt | FastAPI (Python); Nuxt — frontend | CV-модели (PyTorch, Ultralytics, transformers) работают в Python; отдельный Node-сервис добавил бы лишний сетевой переход |
| pgvector | Qdrant | коллекция на ракурс, фильтр по payload (`main_photos_only`), ~23 тыс. векторов на ракурс без настройки индексов PostgreSQL |
| Strapi CMS | каталог из JSON-дампа в PostgreSQL | каталог приходит дампом; `db-init --prune` приводит базу к нему при каждом запуске |
| SigLIP 2 | SigLIP2-base-384 + свой адаптер | совпадает с рекомендацией, адаптер дообучен на каталоге |
| Docker | Docker Compose | совпадает |
