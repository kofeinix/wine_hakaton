# Сканер вин

Веб-сервис, который находит российское вино по фотографии бутылки или этикетки. Пользователь
фотографирует вино в магазине или ресторане и получает карточку: производитель, регион, сорт,
крепость, температура подачи, сочетания с блюдами, отзывы и похожие вина. Каталог — 2107 вин
портала «Своё Вино».

Подробно о пайплайне и слоях — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Как это работает

```
фото ─► детекция бутылки и этикетки (YOLO)
     ─► эмбеддинги трёх ракурсов: всё фото, бутылка, этикетка (SigLIP2-384 + дообученный адаптер)
     ─► поиск похожих фото в каталоге (Qdrant, ~23 тыс. фото)  ─┐
     ─► распознавание текста этикетки (vision-LLM, по желанию) ─┴► реранк ─► результат
```

1. **Кропы.** YOLO находит на фото бутылку и этикетку. Если в кадре полка с несколькими винами,
   пользователь может нажать на нужную этикетку или обвести бутылку рамкой.
2. **Визуальный поиск.** Для каждого ракурса считается эмбеддинг SigLIP2 и ищутся ближайшие фото
   каталога. Каталог дополнен сгенерированными ракурсами (бутылка в разных сценах и при разном свете),
   поэтому поиск устойчив к фону и освещению. Скоры фото агрегируются в скор вина.
   Поверх SigLIP2 — свой адаптер векторов (`scripts/train_view_adapter.py`): обучен на каталоге сводить
   фото «из жизни» с фото того же вина и разводить соседние вина одной линейки. На отложенных фото
   Vivino он поднял точность поиска с 89,4% до 92,4% (top-1, вместе с распознаванием текста).
3. **Текст этикетки.** Vision-LLM читает этикетку; найденные производитель, название, сорт, цвет,
   сахар и крепость уточняют порядок кандидатов. Если визуальный результат и так уверенный,
   распознавание пропускается. Без LLM сервис работает — только по изображению.
4. **Результат.** Лучшее совпадение с карточкой вина, похожие варианты и диагностика поиска
   (рамки детекции, время этапов, разложение скора).

Во вкладке «Сомелье» — подбор без нейросети: для чего вино, что на столе и каким оно должно быть, фильтры каталога (тип, цвет,
сахар, регион, сорт, рейтинг), поиск по названию с исправлением опечаток и список вин по регионам.
У каждого вина в подборке указано, почему оно подошло, — по полям его карточки.

Винные термины в названии и описании вина подчёркнуты: по нажатию справа снизу открывается
чат-справочник с определением. В нём же есть поиск по словарю (140 терминов, источник —
[словарь винных терминов Luding](https://luding-group.ru/slovar-vinnykh-terminov/)).

Для пользователей есть кабинет: история сканирований (без входа — временная, после входа
сохраняется в аккаунт), избранное, оценки с комментариями и напоминания «вы недавно смотрели
вина — что-то взяли?».

**Стек:** Nuxt (Vue) · FastAPI · PostgreSQL · Qdrant · MinIO · Redis · YOLO · SigLIP2 · vision-LLM
(локально Qwen3-VL или любой OpenAI-совместимый API).

## Качество поиска

Две проверки: публичный датасет «полевых» фото организаторов и наши отложенные фото Vivino.

**Как читать F1.** На каждом фото одно правильное вино, поэтому F1 для top-1 совпадает с долей верных
ответов. F1 для top-5 по обычной формуле `2·P@5·R@5 / (P@5 + R@5)` не может быть больше 0,333:
точность P@5 не выше 1/5, даже если правильное вино всегда в пятёрке. Поэтому рядом приводим и
долю фото, где правильное вино попало в top-5 (Recall@5). Уверенность (`similarity`, 0–1) — итоговый
скор, делённый на максимально возможный в этом поиске; её и отрыв от второго места API отдаёт в
`/api/v1/search/image/extended`.

### Датасет организаторов (реальные фото с полок)

100 фото: 67 фото 48 вин из каталога и 33 фото вин, которых **нет на сайте «Своё Вино»**. Прогон —
скриптом организаторов `eval/participant_test.sh` на локальном сервисе (Docker на ноутбуке, модели на
CPU, OCR — облачная `glm-5.3-flash` через RouterAI), кеш распознанного текста перед прогоном пуст.

**Вина из каталога (67 фото):**

| Метрика | Значение |
|---|---|
| Доля верных ответов top-1 (цель ТЗ — 90–100%) | **98,5%** (66 из 67) |
| F1 для top-1 | **0,985** |
| F1 для top-1 по винам (macro, 48 вин) | 0,972 |
| Правильное вино в top-5 (Recall@5) | **100%** (67 из 67) |
| F1 для top-5 (формула выше) | 0,333 — максимум возможного |
| Вин, где верны все фото | 47 из 48 |

Единственная ошибка — «АРАТТИ Каберне по-белому»: в каталоге два вина с одинаковым названием, правильное
на 2-м месте.

**Уверенность и отрыв от второго места** (медианы):

| | Уверенность top-1 | Отрыв top-1 − top-2 |
|---|---|---|
| Верные ответы (66) | 0,81 | 0,127 |
| Ошибка (1) | 0,89 | 0,056 |
| Вина нет в каталоге (33) | 0,48 | 0,038 |

**Вина не из каталога (33 фото).** Порога «вино не найдено» пока нет: сервис всегда возвращает самое
похожее вино, поэтому на этих фото верных ответов нет и **F1 для «нет в каталоге» = 0**. Уверенность у
них заметно ниже. Если отвечать «не найдено» при уверенности ниже 0,58, F1 для «нет в каталоге» был бы
0,81, а верных ответов по всем 100 фото — 88% вместо 66%. Это оценка: порог подобран на этих же фото.

**Время ответа** (замер скрипта организаторов, целевой SLA — до 3 с):

| | Среднее | Медиана | p95 | Макс | Быстрее 3 с |
|---|---|---|---|---|---|
| Все 100 фото | 2,98 с | 2,98 с | 5,10 с | 7,52 с | 51 из 100 |
| OCR пропущен — визуальный результат уверенный (32) | 1,37 с | 1,38 с | — | 1,73 с | 32 из 32 |
| С OCR (68) | 3,74 с | 3,38 с | — | 7,52 с | 19 из 68 |

Всё, что дольше 3 с, — ожидание облачной LLM; по изображению сервис отвечает за ~1,4 с.

### Отложенные фото Vivino (наш набор)

537 фото пользователей Vivino, 440 вин (`data/eval`). Проверка без утечек: эти фото **исключены из
индекса каталога** (в рабочем индексе они есть), а **адаптер обучен без них** — теми же параметрами, что
и рабочий. Считали офлайн тем же кодом кропов и эмбеддингов и той же агрегацией, что в сервисе;
распознанный текст — из прошлых прогонов сервиса (есть для 526 фото), OCR пропускается по тем же
порогам, что в сервисе.

| Метрика | Только изображение | Итог (с OCR) |
|---|---|---|
| Доля верных ответов top-1 = F1 для top-1 | 91,4% | **92,4%** |
| F1 для top-1 по винам (macro, 440 вин) | — | 0,924 |
| Правильное вино в top-5 (Recall@5) | 99,6% | **99,8%** |
| F1 для top-5 (формула выше) | 0,332 | 0,333 |

Уверенность top-1 (медиана): верные ответы 0,84, ошибки 0,79; отрыв от второго места: верные 0,186,
ошибки 0,023. OCR понадобился в 173 поисках из 537.

Фото Vivino в основном сняты вплотную к этикетке (68% против 18% на фото организаторов), поэтому по
одному изображению здесь выше, чем на фото с полок (91% против ~88%), а OCR добавляет меньше.

## Запуск

### Что нужно

- Docker с Docker Compose v2 (Docker Desktop на macOS/Windows);
- ~15 ГБ свободного места, для Docker — от 8 ГБ памяти;
- интернет при первом запуске: скачиваются модели (~1,7 ГБ) и данные (~5,2 ГБ);
- по желанию — [LM Studio](https://lmstudio.ai) или [Ollama](https://ollama.com) для распознавания текста.

### Шаги

```bash
git clone https://github.com/kofeinix/wine_hakaton.git
cd wine_hakaton
cp .env.example .env
docker compose up -d --build
```

Первый запуск занимает время: сервисы `models-init` и `data-init` скачивают модели и данные, затем
заполняются база, Qdrant и хранилище фото. Следить за прогрессом:

```bash
docker compose logs -f models-init data-init qdrant-init minio-init app
```

Когда в логах `app` появится `Uvicorn running`, откройте:

- **сайт:** http://localhost:5173
- **API (Swagger):** http://localhost:8000/docs

При следующих запусках всё уже скачано и загружено — сервис стартует за минуту.

### Распознавание текста этикеток (по желанию)

Запустите локальную модель Qwen3-VL-4B одним из способов:

```bash
./run_llm.sh            # LM Studio (macOS / Linux)
./run_llm.sh ollama     # Ollama
./run_llm.sh vllm       # Linux с NVIDIA GPU
```

На Windows: `.\run_llm.ps1` или `.\run_llm.ps1 ollama`.

Скрипт скачает модель, запустит сервер и выведет две строки для `.env` (`LLM__BASE_URL`,
`LLM__MODEL_NAME`). Для LM Studio значения из `.env.example` уже подходят. Без GPU можно взять облачный
OpenAI-совместимый API — пример закомментирован в `.env.example`.

Если LLM не запущена или эти переменные не заданы, сервис всё равно стартует (в логе `app` —
предупреждение) и ищет только по изображению. Доступность LLM проверяется при старте `app`, поэтому
после изменения `.env` пересоздайте контейнер, а если LLM просто запустили позже — перезапустите его:

```bash
docker compose up -d app        # после изменения .env
docker compose restart app      # .env не менялся, LLM запущена позже
```

### Проверочный скрипт организаторов

Сервис сразу отвечает на адрес, который скрипт использует по умолчанию —
`POST http://127.0.0.1:8080/v1/eval/predict` (порт задаётся `EVAL_PORT` в `.env`):

```bash
cd eval
bash participant_test.sh --images-dir ./queries --manifest ./queries.tsv \
  --endpoint 'http://127.0.0.1:8080/v1/eval/predict' --output ./predictions.jsonl
```

Ответ — `{"slug": "..."}`, в историю поиска такие запросы не пишутся. Скрипт ждёт ответ не дольше
10 секунд, поэтому распознавание текста ограничено `SEARCH__OCR_BUDGET_SECONDS` (7,5 с): если LLM не
успела, сервис отвечает по изображению. Модели прогреваются при старте, первый запрос не ждёт их загрузки.

Все настройки — в `.env` (шаблон — `.env.example`). Для запуска через Docker Compose менять ничего не
обязательно. Вложенные параметры пишутся через двойное подчёркивание: `РАЗДЕЛ__ПАРАМЕТР`. После
изменения `.env` выполните `docker compose up -d`.

**Порты на хосте**

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `FRONTEND_PORT` | `5173` | сайт |

| `AUTH__ACCESS_TOKEN_TTL_MINUTES` | `10080` | срок жизни токена (7 дней) |

| `NOTIFICATIONS__CHECK_INTERVAL_SECONDS` | `60` | как часто проверять |

**Прочее.** `VITE_ALLOWED_HOSTS` — домены или IP (кроме localhost), с которых открывают сайт, через
запятую; `*` — любые (нужно, например, чтобы открыть сайт с телефона по IP компьютера). `LOG_LEVEL` —
уровень логов API (`INFO`).

**Логи API** — [structlog](https://www.structlog.org/), по умолчанию одна строка JSON на запись
(`LOG_FORMAT=json`; `LOG_FORMAT=text` — читаемый текст). Логи uvicorn и библиотек идут в том же формате.
Поля: `ts` (UTC), `level`, `logger`, `event` — имя события (`http_request`, `image_search`, `visual_search`,
`ocr_text`, `ocr_rerank`, `llm_call`, `login`, `register`, `favorite_add`, `review_save`, `http_error`, …),
внутри запроса — `request_id` и `actor`, дальше данные события отдельными полями (`status`, `duration_ms`,
`top1_slug`, `timings_ms`, …), у ошибок — `exception` (трассировка без локальных переменных).
Пример: `docker compose logs app --no-log-prefix | jq 'select(.event=="image_search")'`.
У каждого запроса свой `request_id` (приходит в заголовке ответа `X-Request-ID`; свой id
можно передать тем же заголовком) и автор: `user:<uuid>` или `anon:<хеш cookie>`. По одному `request_id` видно
всё, что было в запросе: строка доступа (метод, путь, имена параметров, статус, время, размер
запроса и ответа), итог поиска (top-1, скор, OCR, время этапов), вызов LLM, действия пользователя
(регистрация, вход, избранное, отзывы, достижения) и причины ошибок 4xx.
Личные данные не пишутся: ни IP, ни email, ни пароли, ни тексты комментариев. Запросы `/health` и
фото каталога — на уровне `DEBUG`.

## Дообучение: адаптер векторов SigLIP2

SigLIP2 обучен на общих картинках: фото бутылки «из жизни» (полка, руки, свет) и фото того же вина
в каталоге он считает недостаточно похожими, а соседние вина одной линейки — слишком похожими. Вместо
дообучения всей модели мы учим небольшой адаптер поверх её векторов — `f(x) = normalize(x + B·A·x)`,
ранг 64, свой для каждого ракурса (всё фото, бутылка, этикетка). Он применяется одинаково к фото каталога
(при загрузке в Qdrant) и к запросу; файл весит 1 МБ и лежит в репозитории: `models/adapter/siglip2_384_views.npz`.

**Данные** — эмбеддинги фото каталога, метка — только `wine_id`, ручной разметки нет:

| источник | фото (всё фото / бутылка / этикетка) | роль |
|---|---|---|
| главное фото с портала | 2107 / 1921 / 2047 | позитив |
| сгенерированные сцены (полка, стол, в руках × 3 света) | 18963 / 18867 / 18227 | якорь и позитив |
| фото с Яндекса | 2379 / 1883 / 2101 | якорь и позитив |
| фото пользователей Vivino (`data/eval`) | 537 / 406 / 482 | якорь и позитив; при проверке — отложены |

Пара «якорь — позитив» — два разных фото одного вина; негативы — остальные вина батча, а батч собирается
из похожих вин (случайное вино + его ближайшие соседи по индексу), чтобы учиться различать вина одной линейки.
Функция потерь — симметричный InfoNCE. Картинки, совпадающие с фото другого вина (косинус > 0,98), выброшены.

**Проверка.** Адаптер обучен без фото Vivino, на них — top-1 ближайшего фото каталога по ракурсу:

| ракурс | SigLIP2-384 | + адаптер |
|---|---|---|
| всё фото | 64,2% | 81,6% |
| бутылка | 70,0% | 85,2% |
| этикетка | 84,6% | 91,3% |

Весь поиск (ракурсы, агрегация, распознавание текста) на тех же 537 фото: фото Vivino исключены из
индекса, адаптер обучен без них (подробнее — в разделе «Качество поиска»):

| вариант | только изображение | с текстом этикетки |
|---|---|---|
| SigLIP2-384 | 84,0% | 89,4% |
| SigLIP2-384 + адаптер | 91,4% | 92,4% |

Итоговый адаптер обучен на всех фото, вместе с Vivino. Воспроизвести можно на хосте, в окружении
проекта (`uv sync`). Эмбеддинги уже скачаны `data-init`; пересчитывать их нужно, только если
менялись фото каталога (`data/images_extended`) — это около 35 минут на Apple M4. Обучение адаптера
занимает около минуты на CPU.

```bash
uv run python scripts/index_siglip2_views_qdrant.py --model-dir models/siglip2_384 \
  --output-dir data/embeddings/siglip2_384 --collection-encoder siglip2_384   # эмбеддинги каталога (необязательно)
uv run python scripts/train_view_adapter.py                                   # проверка + финальный адаптер
docker compose up -d --build                                                  # коллекции с новой версией адаптера
```

## Ограничения

**Поиск**

- Ищем только среди 2107 вин каталога. Если вина в каталоге нет, сервис всё равно возвращает самое
  похожее (`status: found`): порога «вино не найдено» пока нет, на фото вин не из каталога F1 = 0 (см.
  «Качество поиска»). Уверенность видна в `similarity` и в отрыве от второго результата.
- «Похожие варианты» — следующие кандидаты того же поиска, то есть визуально похожие вина, часто той
  же линейки. Подбора аналогов из других виноделен по сорту и стилю в сканере нет (он есть во вкладке
  «Сомелье» через фильтры).
- В каталоге 37 групп (76 вин) с одинаковыми производителем, названием, цветом и сахаром: по этикетке
  они почти неотличимы, и ошибка между ними возможна даже при верно прочитанном тексте. Год урожая
  OCR не учитывает — в каталоге он указан только у 34 вин.
- На фото полки выбирается одна бутылка — ближе к центру и крупнее. Если нужна другая, её выбирают
  нажатием на рамку или обводят вручную.
- Фото Vivino лежат в рабочем индексе, и рабочий адаптер обучен на них. Поэтому метрики на Vivino
  считаются только офлайн — без этих фото в индексе и с адаптером, обученным без них; прогон сервиса
  на `data/eval` через `scripts/eval_search.py` завышает точность.
- Датасет организаторов — 100 фото (67 из каталога): на такой выборке одна ошибка — это 1,5 п.п.

**Распознавание текста (OCR)**

- Нужна отдельно запущенная vision-LLM (`./run_llm.sh`) или облачный API. Без неё поиск идёт только
  по изображению, точность ниже (на Vivino 91,4% против 92,4%; на фото с полок разница больше).
- OCR — главный вклад во время ответа: с ним медиана 3,4 с, без него 1,4 с (облачная LLM).
- Доступность LLM проверяется один раз при старте: если LLM запустили позже, перезапустите `app`.
- К LLM идёт не больше одного запроса одновременно (`RATE_LIMITER__LIMITERS`); ответ ждём не дольше
  7,5 с (`SEARCH__OCR_BUDGET_SECONDS`), дальше — по изображению.
- Облачный API получает кроп этикетки с фото пользователя.

**Скорость и железо**

- Модели YOLO и SigLIP2 обрабатывают запросы по очереди (один поток): параллельные поиски ждут друг
  друга. Сервис рассчитан на демонстрацию, а не на нагрузку.
- В Docker на macOS GPU Apple (MPS) недоступен — модели считаются на CPU. NVIDIA GPU используется,
  если контейнеру проброшен доступ к нему (в `docker-compose.yml` это не настроено).

**Данные и каталог**

- Первый запуск требует интернета: ~1,7 ГБ моделей и ~5,2 ГБ данных с Hugging Face, релизов
  Ultralytics и Яндекс Диска.
- Рейтинг в карточке — народный рейтинг портала «Своё Вино», он есть у 886 из 2107 вин. Рейтинга
  Роскачества в выданном дампе нет.
- Новое вино в поиске появится только после расчёта эмбеддингов его фото
  (`scripts/index_siglip2_views_qdrant.py`) и перезаливки Qdrant; изменения каталога в «Сомелье»
  видны после перезапуска `app`. Миграций схемы БД нет.
- Скрипты генерации сцен (`generate_*_views.py`) требуют GPU и пакетов `diffusers`, `torchao`, которых
  нет в `pyproject.toml`. Для запуска сервиса они не нужны — их результат входит в скачиваемые данные.

**Безопасность**

- Сборка демонстрационная: фронтенд работает в dev-режиме Nuxt, авторизация — email и пароль без
  подтверждения почты. Если не задать `AUTH__JWT_SECRET`, используется небезопасный секрет по
  умолчанию (в логе будет предупреждение).

## Если что-то пошло не так

- **Порт занят.** Поменяйте нужный порт в `.env` (`APP_PORT`, `FRONTEND_PORT`, `DATABASE__PORT`,
  `QDRANT__PORT`, `MINIO__PORT`, `REDIS__PORT`) и выполните `docker compose up -d`.
- **Данные не скачались.** Скачайте вручную из [папки на Яндекс Диске](https://disk.yandex.ru/d/TW3su5DtKTNtfQ)
  и положите: `original.npz`, `bottle_crop.npz`, `label_crop.npz` — в `data/embeddings/siglip2_384/`,
  `photos.tar.gz` и `photos_webp.tar.gz` (главные фото в webp, необязательный) — в `data/`.
  Затем `docker compose up -d`.
- **Модели не скачались.** Повторите `docker compose up models-init` и посмотрите его лог.
- **Текст этикетки не распознаётся** (в диагностике поиска «OCR · выключен»). Проверьте, что LLM
  запущена и её адрес в `.env` верный: из контейнера локальная LLM доступна как
  `http://host.docker.internal:<порт>/v1`, а не `localhost`. Затем перезапустите `app` (см. выше) — в
  логе `app` не должно быть предупреждения `LLM ... is unavailable`. Без LLM поиск работает по изображению.
- **Поиск медленный.** Проверьте в логе `app`, на каком устройстве загружены модели (`YOLO model loaded:
  ... on cpu`, `Loading SigLIP2 model ... on cpu`); устройство можно задать `YOLO__DEVICE` и
  `EMBEDDINGS__DEVICE`.
- **Начать с нуля:** `docker compose down -v` удалит базу, векторы и фото (скачанные файлы в `data/`
  и `models/` останутся), затем `docker compose up -d`.

## Структура репозитория

```
frontend/          сайт (Nuxt)
src/               API: поиск, пользователи, работа с моделями и хранилищами
scripts/           подготовка данных и инициализация сервисов
data/db/           каталог вин (JSON) — загружается в PostgreSQL при старте
models/yolo/       своя модель детекции этикеток (остальные модели скачиваются)
models/adapter/    дообученный адаптер векторов SigLIP2 (scripts/train_view_adapter.py)
run_llm.sh / .ps1  запуск локальной vision-LLM
ARCHITECTURE.md    пайплайн поиска и границы слоёв
```

Большие данные (фото каталога, эмбеддинги) в репозиторий не входят — их скачивает `data-init`.
Материалы организаторов (`eval/`: проверочный скрипт и фото) тоже не входят: положите их в папку
`eval/` в корне репозитория.

Скрипты в `scripts/`, которыми собраны данные (для воспроизведения):

| Скрипт | Что делает |
|---|---|
| `prepare_image_views.py` | вырезает бутылку и этикетку на фото каталога |
| `generate_qwen_image_edit_views.py`, `generate_flux2_klein_views.py` | генерируют дополнительные ракурсы бутылок |
| `index_siglip2_views_qdrant.py` | считает эмбеддинги SigLIP2 фото каталога по ракурсам (`--model-dir models/siglip2_384 --output-dir data/embeddings/siglip2_384`) |
| `train_view_adapter.py` | обучает адаптер векторов на эмбеддингах каталога, с проверкой на отложенных фото Vivino |
| `download_main_webp.py` | скачивает главные фото вин в webp (прозрачный фон) с сайта портала |
| `build_photos_archive.py` | собирает архив фото для MinIO (`--webp` — отдельный архив webp) |
| `enrich_wines_from_site.py` и др. `enrich_*` | дополняют карточки вин данными портала |
| `import_wine_terms.py` | собирает словарь винных терминов в `data/db/wine_terms.json` |
| `eval_search.py` | оценка качества поиска на отложенной выборке фото |
| `init_database.py`, `init_qdrant.py`, `prepare_models.py`, `download_data.py` | запуск (вызываются из Docker Compose) |
